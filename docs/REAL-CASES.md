# Real dependency upgrades, reproducible offline

Lockray includes four complete before/after npm lockfile pairs from public upstream dependency-update commits and their first parents. These are historical source snapshots with unchanged bytes, not updates generated by running `npm update` locally. No project dependencies were installed or executed to collect or compare them.

The current v0.2 source exposes them in the browser's **Real upgrade cases** picker. Each selection loads both files from the application's static host, checks their pinned SHA-256 values, and analyzes them locally. Browser hash verification uses Web Crypto, so use HTTPS hosting or the loopback development URL. The [manifest](../samples/real/manifest.json) records exact commit IDs, immutable raw-file URLs, dates, byte lengths, expected counts, and retained licenses.

## What the checks establish

The default real-case tests use two independent checks alongside the pinned manifest:

1. **Raw JSON comparison.** Node's `util.isDeepStrictEqual` compares parsed original descriptors, independently of Lockray's parsing and stable serialization. The check compares the complete changed-location/status set and every summary count. Self-comparison, reversal, and repeated runs check basic invariants.
2. **Native Node lookup directories.** `createRequire(...).resolve.paths()` supplies the running Node executable's ascending lookup directories for a virtual package location. The test matches those directories against recorded slots without loading package code. It checks each reported chain edge, shortest path length, all reachable root owners, and root-group counts.

The independent graph deliberately asks Node about a non-builtin probe, then appends each declared dependency name to those lookup directories. Asking `resolve.paths('string_decoder')` directly returns `null` for Node's built-in module, even though a lockfile can contain a declared npm shim with that same name. That was a test-oracle issue, not a Lockray product defect: the graph here describes declared installed packages, not which module a runtime import chooses. The npm implementation check below confirmed the corrected interpretation.

These checks operate on committed local snapshots. They do not access a registry, inspect tarballs, run lifecycle scripts, or reproduce npm's dependency-solving process.

## Reproduce the default tests

Use Node.js 22 or newer from a source checkout containing the v0.2 examples:

```sh
# Only the real-case byte, diff, chain, and owner checks.
npm run test:real

# Include parser, CLI, and focused regression tests as well.
npm test

# Review the largest historical change from the CLI.
node bin/lockray.js samples/real/axios-tree/before.package-lock.json \
  samples/real/axios-tree/after.package-lock.json \
  --format markdown --output axios-review.md
```

There is no dependency installation step and the tests work without registry access. Browser example loading is an ordinary same-host request for bundled files; file processing remains local.

## Optional cross-check against npm

Maintainer validation also used an **already installed `@npmcli/arborist` 9.7.0** and its `loadVirtual()` implementation. For all four pairs, the supported installed targets, reported shortest paths, and root-owner sets agreed with no differences. The [recorded machine-readable result](real-cases-npm.json) contains the per-snapshot inventories and empty difference lists. This is a check against that npm implementation and these snapshots, rather than a claim of universal package-manager equivalence.

The optional script is [`scripts/check-npm-edges.js`](../scripts/check-npm-edges.js). Supply an absolute path to an Arborist installation you already have; the placeholder below is not a download command:

```sh
node scripts/check-npm-edges.js --help

node scripts/check-npm-edges.js \
  --arborist /absolute/path/to/already-installed/@npmcli/arborist

# Restrict the check to one saved pair.
node scripts/check-npm-edges.js \
  --arborist /absolute/path/to/already-installed/@npmcli/arborist \
  --case marked
```

The script writes a lockfile and root descriptor into a temporary directory, calls `loadVirtual()` with offline mode, auditing/funding disabled, and scripts ignored, then removes the temporary directory. It does not call `reify()`, install upstream dependencies, or add Arborist to Lockray's runtime/build dependencies. Exit codes are `0` for agreement, `1` for oracle differences, and `2` for configuration/input errors.

## Corrections driven by the investigation

**Bundled integrity noise.** The Marked update changes nine `inBundle` locations that have no individual integrity in either snapshot. v0.1 emitted nine missing-integrity signals. v0.2 produces one coverage note describing those locations and explicitly leaves package contents and the parent artifact unverified. A non-bundled missing value, or loss of a previously recorded value even within a bundle, still receives a signal. No safety conclusion follows from a lower signal count.

**Duplicate root declarations.** Focused npm/Arborist checks following the real-project investigation showed that a name declared in both `dependencies` and `devDependencies` uses the development declaration as its effective root edge. Lockray now follows development > optional > production > peer, retains every declaration, and reports changes to an overridden declaration even when the effective declaration and installed version stay the same. One name still creates one owner group.

**Sibling file/link targets.** npm-generated lockfiles can contain target entries such as `../sibling`, including targets with their own `node_modules` metadata. These are now accepted as opaque target descriptors instead of being rejected by project-slot path checks. Lockray does not expand them or read external files; actual installed slots retain strict validation.

The last two corrections have targeted npm-shaped regression fixtures in addition to the four unmodified public snapshots. They should not be confused with upstream dependency changes authored by Lockray. The exact behavior and remaining limits are documented in [MODEL.md](MODEL.md).
